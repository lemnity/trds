# Memory — постоянный контекст проекта

Этот файл — компактная память для разработчика/Claude Code между сессиями. Обновлять при каждом подтверждённом продуктовом решении и завершении крупного этапа. Не заменять предположениями ответы театра.

## 1. Проект

- Проект: самостоятельный сайт и билетная система театра «Турдус».
- Домен из исходного ТЗ: `teatrturdus.ru`; точное написание и владение должны быть подтверждены.
- Цель: перейти от сайта на Tilda к своему сайту и поэтапно заменить Ticketscloud для продажи билетов.
- Владелец персональных данных: театр; исполнитель обрабатывает данные по договорному поручению.
- Основной язык интерфейса: русский.
- Все суммы: RUB, хранение в целых копейках.
- Хранилище персональных данных/backup: инфраструктура в РФ.

## 2. Согласованный scope

Входит: дизайн с анимацией; главная; афиша; страницы спектаклей; «О театре»; корпоративы; контакты; перенос контента/домена с Tilda; документы и cookie consent; SEO и аналитика; продажа билетов по категориям; выбор мест на схеме для зала Дома актёра (решение 15.10.2026); карта и СБП; чеки 54-ФЗ через поддерживаемую схему банка; QR-билет на email; личный кабинет, бонусы и возвраты; управление афишей/ценами/контентом; бонусная программа; канбан корпоративных заявок.

Не входит: схемы залов других площадок, абонементы, полноценная CRM, рассылки, мини-приложение VK, сканер/контроль входа по QR. QR отображает билет, но check-in не предусмотрен.

## 3. Базовая архитектура

- Next.js App Router + TypeScript + Payload CMS 3.x в одном репозитории/приложении.
- PostgreSQL 16 — общая БД; Payload владеет CMS-коллекциями, commerce-таблицы — через отдельные доменные миграции.
- Версии стека закреплены в T-005 (14.10.2026): Node 24.21.0, pnpm 10.34.6 (corepack), Payload 3.90.2, Next.js 16.3.8, React 19.2.8, TypeScript 5.9.3. Источник совместимости — peerDependencies `@payloadcms/next`/`@payloadcms/ui` (Next `>=16.3.3 <17`), а не текст документации. Утверждение «Payload требует Node 24.15+/Next 16.4+» не подтвердилось. Подробности, overrides безопасности и принятые риски audit — `architecture.md` §2. Новые версии берём не моложе 14 дней.
- Docker Compose: `app`, `worker`, `postgres`, `caddy`.
- Медиа/резервные копии — S3-совместимое хранилище в РФ.
- Сайт, API, кабинет и Payload Admin в Next.js; worker отдельно для outbox/expiry/reconciliation.
- Email через адаптер; выбранный сервис проверить по доставке/условиям обработки данных.
- Единственный payment adapter в MVP: ЮKassa или Т-Банк, в зависимости от договора театра и облачной кассы.

## 4. Критические системные инварианты

1. Не выпускать билеты на основании redirect/фронтенда; только после подтверждённого сервером статуса и проверки суммы/валюты/order metadata у провайдера.
2. Не допускать oversell: inventory reservation в транзакции; `sold + held <= capacity`.
3. Не считать webhook доставленным ровно один раз: дедупликация обязательна.
4. Если платёж успешен после освобождения hold, не превышать capacity; выделить оставшуюся квоту или запустить возврат/ручной разбор.
5. Внешние уведомления/письма — через outbox и retry. Ошибка email не отменяет подтверждённый заказ.
6. Возврат нельзя объявлять завершённым без подтверждения провайдера.
7. Бонусы — immutable ledger; резервы блокируют повторное списание; повторные события не должны создавать дублей.
8. Персональные данные и секреты не помещать в QR, клиентский bundle или обычные логи.
9. Роли должны проверяться на сервере; MFA обязательна для админов.
10. Не выключать Ticketscloud до приёмки live-покупок, возврата и чеков.

## 6. План релиза

- Этап 1 (до 4 недель): сайт, дизайн, Payload, контент, документы, SEO, аналитика, домен; Ticketscloud продолжает продавать.
- Этап 2 (до 3 недель после подключения банка): checkout, бронь, эквайринг, чеки, webhook, билеты/QR, email, кабинет, возвраты; 3–5 реальных тестовых покупок + 1 возврат.
- Этап 3 (до 1 недели): лояльность, рефералка, канбан, обучение; отключить Ticketscloud после приёмки.
- Сроки зависят от банка и скорости согласования контента/правил.
