# Передача проекта театру «Турдус»

Что театр получает, какие доступы и аккаунты нужно завести на себя и какие решения ещё за
театром (T-076). Эксплуатация — `docs/runbook.md`, работа сотрудников в админке —
`docs/admin-guide.md`.

Состояние на 26.10.2026: продажа на сайте **не включена** — банк не выбран (T-001), фискальная
схема не подтверждена (T-002). Сайт, CMS, кабинет, бонусы, возвраты и учебный банк для проверки
готовы и покрыты тестами.

---

## 1. Что передаётся

### Репозиторий

- GitHub `lemnity/trds`, ветка `main`. Права владельца репозитория (Owner / Admin) — на аккаунт
  театра; исполнитель — участник с правами по договору.
- Документация в корне: `PRD.md` (требования), `architecture.md`, `design.md`, `rules.md`
  (обязательные правила разработки), `tasks.md` (статусы задач), `memory.md` (решения и открытые
  вопросы); `docs/runbook.md`, `docs/admin-guide.md`, этот файл; модули — `src/modules/README.md`.
- Стек: Next.js 16 + Payload CMS 3 + PostgreSQL 16, Node.js 24, pnpm 10 (версии закреплены в
  `package.json` и `pnpm-lock.yaml`).

### CI (GitHub Actions)

- `.github/workflows/ci.yml` — на каждый push в `main` и pull request: формат, lint, проверка
  типов, unit-тесты, production-сборка; проверка `docker-compose.yml` и сборка образа; e2e
  (Playwright: свой одноразовый PostgreSQL и сервер с учебным банком); `pnpm audit --prod`.
- `.github/workflows/pages.yml` — статическое демо на GitHub Pages (без базы и оплаты, демо-данные).
  После запуска сайта на своём домене его можно отключить.
- Секретов в CI нет: тестовые генерируются на каждый прогон.

### Сервер: Docker / compose

`docker-compose.yml` (подробности — `docs/runbook.md` §1):

| Сервис | Назначение |
|---|---|
| `caddy` | HTTPS (сертификат Let's Encrypt автоматически для `SITE_DOMAIN`), единственный с открытыми портами 80/443 |
| `app` | сайт и админка (Next.js + Payload), `/api/health` |
| `worker` | фоновые задачи: письма, сверка оплат и возвратов, сгорание бонусов, чистка |
| `postgres` | база данных, только во внутренней сети |
| `backup` | ежедневная резервная копия |

Запуск — `docker compose up -d --build` (README, раздел «Production-окружение»). Сервер — в РФ
(персональные данные); размер выбирается вместе с хостингом (T-004, T-012).

## 2. Переменные окружения (`.env` на сервере)

Файл `.env` лежит только на сервере, в git не попадает. Образец без секретов — `.env.example`.
Значения секретов хранятся у театра (менеджер паролей/сейф), а не только у исполнителя.

| Переменная | Зачем | Секрет |
|---|---|---|
| `PAYLOAD_SECRET` | Главный секрет приложения (≥ 32 символа, `openssl rand -hex 32`): сессии админки, второй фактор сотрудников, подпись QR-билетов и ссылок из писем, отпечатки номеров сертификатов, ссылки на статус заказа. **См. §3 — менять с осторожностью** | да |
| `POSTGRES_PASSWORD` | Пароль базы (`openssl rand -hex 16`); из него compose собирает `DATABASE_URL` | да |
| `DATABASE_URL` | Подключение к базе (локальная разработка; в compose задаётся само) | да |
| `SITE_DOMAIN` | Домен сайта для HTTPS (Caddy) | нет |
| `HTTP_PORT`, `HTTPS_PORT` | Порты Caddy (80/443) | нет |
| `HSTS_MAX_AGE` | Только для `localhost` (0). В production не задавать — 1 год | нет |
| `NEXT_PUBLIC_SITE_URL`, `PUBLIC_SITE_URL` | Адрес сайта: возврат из банка, ссылки в письмах, SEO. В production обязателен | нет |
| `PAYMENT_PROVIDER` | Банк. Пусто — оплаты нет (сайт честно говорит «не подключена»); `fake` — учебный банк, в production запрещён. Адаптер настоящего банка — после T-001; его ключи (идентификатор магазина, секрет, ключ уведомлений) добавятся сюда же | да (ключи банка) |
| `CHECKOUT_HOLD_TTL_SECONDS` | Только для разработки: короткая бронь | нет |
| `EMAIL_PROVIDER`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` | Отправка писем (билеты, возвраты, уведомления театру) через SMTP почтового сервиса | да (`SMTP_PASSWORD`) |
| `EMAIL_FROM`, `EMAIL_REPLY_TO` | Отправитель и адрес для ответов (домен с SPF/DKIM) | нет |
| `THEATRE_NOTIFY_EMAIL` | Почта театра для писем «Заказ требует проверки» и о новых заявках на корпоративы | нет |
| `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` | Вход через Яндекс ID. Пусто — кнопки нет | да (`YANDEX_CLIENT_SECRET`) |
| `NEXT_PUBLIC_YM_ID` | Номер счётчика Яндекс Метрики (загружается только после согласия на cookie) | нет |
| `CMS_SYSTEM_ADMIN_EMAILS` | Почты системных администраторов CMS (назначают администраторов, сбрасывают чужой второй фактор). Первый сотрудник становится им автоматически | нет |
| `MEDIA_DIR` | Папка загрузок «Медиа» до подключения S3 | нет |
| `CONTENT_SOURCE` | Источник данных сайта (`cms` — строго CMS; пусто — по умолчанию) | нет |
| `LOG_LEVEL` | Подробность логов (`info`) | нет |
| `WORKER_TICK_MS`, `WORKER_HEARTBEAT_MAX_AGE_MS`, `BACKUP_MAX_AGE_HOURS`, `WORKER_HEARTBEAT_FILE`, `BACKUP_STATUS_FILE` | Такт фоновых задач и пороги `/api/health` (в compose заданы) | нет |
| `BACKUP_AT`, `BACKUP_RETENTION_DAYS` | Время ежедневной копии (UTC) и срок хранения | нет |
| `BACKUP_OFFSITE_TARGET` | Внешняя копия в S3 — **заглушка**, пока провайдер не выбран | — |
| `ACCOUNTS_STORE`, `RATE_LIMIT_STORE` | Только для разработки без базы (`memory`); в production не задавать | нет |

**До запуска нужно доделать в `docker-compose.yml`** (сейчас сервисам `app`/`worker` передаются
только база, `PAYLOAD_SECRET`, `LOG_LEVEL` и файлы состояния):

- добавить в общее окружение `app` и `worker` переменные почты, `THEATRE_NOTIFY_EMAIL`,
  `PUBLIC_SITE_URL`, `PAYMENT_PROVIDER` и ключи банка, `YANDEX_*`, `CMS_SYSTEM_ADMIN_EMAILS`;
- `NEXT_PUBLIC_*` (`NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_YM_ID`) встраиваются в сайт **при сборке
  образа** — передать их в сборку (build args в `Dockerfile`), а не только в `.env`;
- медиа: подключить S3 (§5) или хотя бы том для `MEDIA_DIR`, иначе загруженные в админке файлы
  живут внутри контейнера и не попадают в резервную копию;
- применение миграций базы при обновлении: сейчас `pnpm payload migrate` запускается из
  окружения с исходниками (как в e2e), в образе приложения автоматического шага нет — оформить
  процедуру (одноразовый контейнер в сети `backend`) до первого развёртывания.

## 3. Секреты и их смена

- Все секреты — только в `.env` на сервере и в хранилище театра; не в git, не в письмах и
  мессенджерах, не в `NEXT_PUBLIC_*`.
- Доступы, ключи восстановления и копии не должны зависеть только от аккаунта исполнителя.
- **`POSTGRES_PASSWORD`**: сменить пароль роли `trds` в базе (`ALTER ROLE`), затем `.env`, затем
  `docker compose up -d` (app, worker, backup). Сразу после — внеплановая копия (runbook §6).
- **`SMTP_PASSWORD`, `YANDEX_CLIENT_SECRET`, ключи банка**: выпустить новый ключ в кабинете
  сервиса → `.env` → `docker compose up -d app worker` → отозвать старый ключ.
- **`PAYLOAD_SECRET` — менять только при утечке.** Из него выводятся ключи, поэтому смена:
  - выкидывает всех из админки, и **второй фактор всех сотрудников придётся настроить заново**;
  - делает недействительными **QR-коды уже выданных билетов и ссылки из писем** (зрителям
    нужно будет показать билет из кабинета после перевыпуска — инструмента массового
    перевыпуска пока нет);
  - **номера ещё не активированных сертификатов перестанут проверяться** (в базе хранятся только
    отпечатки) — до смены активировать их или после смены перевыпустить партии;
  - сбрасывает ссылки «статус заказа» и вход через Яндекс в процессе.
  Если смена неизбежна — согласовать окно, предупредить кассу, после смены пройти настройку MFA и
  проверить вход, письмо с билетом и активацию сертификата.

## 4. Домен и DNS

- Сайт переезжает с Tilda на `teatrturdus.ru` (точное написание и владелец — подтвердить, T-004).
  Регистратор и доступ к DNS — на театре.
- DNS: запись `A` (и `AAAA`, если есть IPv6) домена на IP сервера; `www` — `CNAME` или отдельная
  запись (решить, куда вести). Порты 80/443 открыты — Caddy сам получит сертификат.
- Почта: у почтового сервиса — SPF, DKIM и DMARC для домена отправителя (`EMAIL_FROM`), иначе
  письма с билетами попадут в спам.
- Переключение домена, 301-редиректы со старых адресов Tilda и отключение Ticketscloud — по
  отдельному чек-листу с разрешения театра (T-075), не автоматически.

## 5. Аккаунты, которые театр заводит на себя

| Сервис | Зачем | Что передать в `.env` / сделать |
|---|---|---|
| **Банк-эквайер** (карта, СБП, онлайн-касса 54-ФЗ) | Приём оплаты и возвраты | Договор, тестовый магазин, ключи API, адрес уведомлений `https://<домен>/api/payments/webhook/<банк>`; подтверждение схемы чеков (T-001, T-002) |
| **Почтовый сервис** (NotiSend, Unisender Go или иной с серверами в РФ) | Письма с билетами и возвратами | SMTP-доступ (`SMTP_*`), подтверждённый домен отправителя, SPF/DKIM |
| **Хранилище S3 в РФ** | Медиа сайта и внешняя копия бэкапов | Бакет, ключ доступа; шифрование копий на стороне сервера; ключи восстановления — у театра (runbook §6, `src/payload/storage.ts`) |
| **Яндекс OAuth** (oauth.yandex.ru) | Вход через Яндекс ID | Приложение «Веб-сервисы», права `login:email` и `login:info`, redirect `https://<домен>/api/auth/yandex/callback` → `YANDEX_*` |
| **Яндекс Метрика** | Аналитика (после согласия на cookie) | Номер счётчика → `NEXT_PUBLIC_YM_ID` (при сборке) |
| **Хостинг / сервер в РФ** | Сам сайт | Доступ администратора к серверу, резервный доступ, мониторинг `/api/health` и места на диске |
| **GitHub** | Код и CI | Организация/аккаунт театра — владелец репозитория |

Первого сотрудника CMS заводит ответственный театра при первом входе в `/admin` — он становится
системным администратором; затем — администраторов, редакторов и кассиров (`admin-guide.md` §2).

## 6. Резервные копии и восстановление

- Ежедневная копия базы (и медиа, когда они настроены) сервисом `backup`, хранение 14 дней;
  контрольные суммы и сверка числа строк при восстановлении.
- Процедуры, команды и результаты учения — `docs/runbook.md` §6–8. Учение проведено локально
  25.10.2026; **на продуктивном сервере повторить до запуска** и затем раз в квартал.
- Внешняя копия вне сервера пока не настроена (S3 не выбран) — до этого копировать вручную
  (`docs/runbook.md` §6). RPO сейчас — до 24 часов; если нужно меньше — решение театра.

## 7. Решения, которые нужны от театра

Без ответов продажа на сайте не включается или работает на временных заглушках (они помечены в
админке и в коде).

**Деньги и чеки**
- [ ] Банк и эквайринг: карта/СБП, договор, API, возвраты, облачная касса (T-001).
- [ ] Бухгалтер: система налогообложения, ставка/вариант НДС, предмет и способ расчёта по 54-ФЗ,
      как отражать бонусы и сертификаты в чеке; сверка бонусного примера (T-002, T-041).
- [ ] Цены билетов и сервисный сбор: сейчас заглушки — с настоящим банком не продаются; входит ли
      сбор в базу начисления 3% и лимита 30% (допущение: не входит).

**Возвраты и бонусы**
- [ ] Правила возврата: срок до начала, частичный возврат, возвращать ли сервисный сбор, место
      снова в продажу — сейчас заглушки, возврат из кабинета выключен (T-003, T-052).
- [ ] Бонусы при возврате: сторно начисленных, возврат потраченных, «долг», если начисленное уже
      потрачено (PRD §5.6, T-064).
- [ ] «Приведи 3 друга»: награда за каждую тройку (сейчас так) или один раз; при полном возврате
      покупки друга до награды он снимается со счётчика, после выданной награды она не
      отбирается — подтвердить (T-062).
- [ ] Поздняя оплата, когда мест уже нет: полный возврат или иное решение (T-048).
- [ ] Сертификаты: срок до активации, номиналы, распространяется ли лимит 30% на сертификатные
      бонусы, продажа на сайте или только в театре (T-066).
- [ ] Гостевые заказы: показывать ли их в кабинете зрителя с той же почтой.

**Контент и юридическое**
- [ ] Тексты документов: политика ПД, cookie, соглашение, правила возврата, реквизиты — от театра
      и юриста (T-022).
- [ ] Номер счётчика Метрики и текст политики cookie (T-036).
- [ ] Часовой пояс дат спектаклей (сейчас Екатеринбург).
- [ ] Дом актёра: нумерация мест, цены 7 категорий, закрытые места; одинаковая ли схема у бара
      «Дом Культуры» (T-049).
- [ ] Фото и биографии труппы, права на медиа, перенос адресов с Tilda (T-004, T-024, T-025).
- [ ] Тексты писем клиенту о статусе заявки на корпоратив (сейчас выключено).
- [ ] Сроки хранения персональных данных (сейчас консервативные значения в `accounts.cleanup`).

**Инфраструктура и люди**
- [ ] Владелец домена, сервера, S3 и почты; хостинг в РФ; staging-сервер (T-004).
- [ ] Внешний мониторинг и кому приходят сигналы; RPO/RTO (runbook §3, §8).
- [ ] Основной и резервный ответственные: админка, касса/возвраты, сервер (T-074) — вписать в
