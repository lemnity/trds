# Rules — правила разработки и работы AI-агентов

Эти правила обязательны для разработчиков, Claude Code и любых coding agents. При конфликте приоритет: безопасность денежных операций и персональных данных → `PRD.md` и `architecture.md` → тесты/миграции → визуальные предпочтения.

## 1. Перед началом

1. Прочитай `PRD.md`, `architecture.md`, `design.md`, `tasks.md`, `memory.md`.
2. Проверь текущую структуру репозитория и версии зависимостей, прежде чем менять архитектуру.
3. Выбери одну задачу из `tasks.md`, выполни её полностью, добавь тесты и отметь статус. Не делай большой несвязанный рефакторинг.
4. Если требование зависит от неизвестного решения театра/банка, реализуй интерфейс и блокирующую настройку, но не выдумывай юридический/бухгалтерский ответ.
5. Перед изменением пакетов проверь официальную совместимость Next.js, Payload, TypeScript и Node.js. Все версии закрепляй lock-файлом.

## 2. Архитектурные границы

- Публичный сайт получает только опубликованный контент через server-side queries.
- Payload CMS — источник редактируемого контента; не хранить деньги, остатки, платёжные переходы или ledger как поля, которые сотрудники могут произвольно изменять в CMS.
- Транзакционные таблицы имеют собственные проверяемые миграции и доменные репозитории.
- HTTP route handler — тонкий слой: parse/validate → auth/rate limit → domain use-case → response.
- Платёжный провайдер скрыт за `PaymentProvider` interface. Бизнес-код не должен зависеть от полей конкретного SDK.
- Внешние эффекты (email, повторная сверка, уведомления и автоматический возврат) планируются через outbox/worker, если их нельзя атомарно объединить с DB-транзакцией.
- Не вызывать внешнее API банка, пока транзакция удерживает DB lock дольше необходимого. Создавать заказ/резерв, фиксировать транзакцию, затем вызывать провайдера; для неопределённого исхода использовать idempotency key и reconciliation.
- Не использовать скрытые побочные эффекты в React Server Components для денежных операций.

## 3. Деньги, остатки и транзакции

- Только целые копейки (`BIGINT` / безопасная проверенная целочисленная арифметика). Запрещены `float` и `parseFloat` для бизнес-расчётов денег.
- Сервер пересчитывает цену и бонусы по данным БД; клиентские `amount`, `discount`, `balance` — не доверенные.
- Любое резервирование, выпуск, списание бонусов и смена статуса заказа выполняются атомарно.
- Inventory должен гарантировать `sold + held <= capacity` в БД/доменной транзакции даже при параллельном checkout.
- Для multi-line checkout блокируй строки в детерминированном порядке и обрабатывай deadlock/serialization failure с ограниченным retry.
- Используй optimistic conditional transition или `SELECT ... FOR UPDATE` в зависимости от доменной операции; не делай «прочитал статус — позже записал новый» без защиты от гонки.
- Статусы переводятся только через одну state-machine/use-case функцию. Не менять статус напрямую из случайного route handler.
- Все интеграции с платежами и возвратами используют idempotency key, если он доступен. Ключ повторного запроса должен быть стабильным в пределах одной операции.
- Дубли webhook безопасны. Не считать доставки exactly-once; проектировать at-least-once с дедупликацией.
- Для late payment после освобождения holds нельзя выдавать билет сверх вместимости. Реализуй выделение остатка или процесс возврата/ручного разбора.
- Исходные bonus ledger entries не редактируются. Коррекции — компенсирующими строками со ссылкой на исходную операцию.

## 4. Безопасность и данные

- Ни один секрет не может попасть в `NEXT_PUBLIC_*`, клиентский JS, HTML, source map, лог или ответ API.
- Не коммить `.env`, credentials, реальные телефоны/email, платёжные payload или токены. Поддерживать `.env.example` только с ключами/описанием.
- Нельзя принимать факт оплаты от redirect URL, параметра query или данных из localStorage.
- Перед выдачей билета получай/проверяй фактический статус платежа у провайдера, сумму, валюту и связь с внутренним заказом.
- Не предполагать, что webhook подписан. Реализовать только схему проверки, предусмотренную официальной документацией выбранного провайдера; при возможности подтвердить объект server-to-server.
- Применяй входную валидацию ко всем публичным API и санитизацию rich text/URL на границе CMS.
- Все customer queries ограничивать текущим customer ID из server-side session; никогда не доверять присланному `customerId`.
- OTP хранить только в хешированном виде; код одноразовый, TTL, лимит попыток и отправки; не раскрывать, существует ли email.
- Cookie сессии: `HttpOnly`, `Secure` на проде, `SameSite`, ограниченный срок, rotation/revocation.
- Проверять CSRF/origin для изменяющих cookie-authenticated запросов.
- Роли проверять в API/access layer, не только в навигации интерфейса.
- MFA обязателен для admin accounts. Recovery flow тестируется отдельно.
- Логировать безопасные идентификаторы и correlation ID; редактировать токены, OTP, email/телефон и секретные поля.
- Сохранять минимальный набор персональных данных. Не собирать поле «телефон», если оно не требуется выбранной схеме чека/бизнес-процессу.
- До подключения поставщика проверять регион хранения, соглашения обработки и юридическую совместимость.

## 5. База данных и миграции

- Не менять структуру продуктивной БД вручную.
- Любая новая таблица/колонка/index/constraint оформляется миграцией.
- Миграции должны быть версионированы, повторяемы только если выбранный механизм это гарантирует, и проверяться на пустой БД и предыдущей версии.
- Не переписывать уже применённые миграции; добавлять следующую.
- Перед потенциально разрушительной миграцией иметь backup и отдельный план отката/forward-fix.
- Обязательны foreign keys, уникальные ограничения, CHECK constraints для инвариантов, где они применимы.
- Проверять индексы для поиска: email_normalized, order number, provider payment ID, status/hold_until, ticket type, outbox status/next_attempt_at.
- Не хранить деньги, балансы или capacity только в кэше.

## 6. API и обработка ошибок

- Используй один формат ошибок (`code`, безопасный `message`, `correlationId`). Не возвращай stack trace и детали БД.
- Ответы различают ожидающее состояние и завершённую операцию.
- Любой route имеет явные схемы входа/выхода и проверку доступа.
- Для webhook: ограничение размера тела, верификация/проверка источника по контракту провайдера, дедупликация, подтверждение фактического платежа, быстрый 2xx после безопасной постановки в очередь; не выполнять долгую отправку email синхронно.
- Timeout внешних запросов, ограниченный retry с backoff и метрика отказов обязательны.
- Не делать бесконечные retries и не игнорировать dead-letter ошибку.

## 7. UI, UX и доступность

- Следовать `design.md`; не вводить новый дизайн-токен/цвет/компонент ради одной страницы.
- Все формы имеют label, inline validation, понятные ошибки, disabled/loading state и success state.
- Поддерживать клавиатуру, focus-visible, reduced motion и адаптивные экраны.
- Критичные действия (оплата, возврат, списание бонусов) всегда показывают сумму/последствие до подтверждения.
- Визуальное «успешно» не заменяет подтверждённый серверный статус.
- Не использовать анимацию, которая мешает чтению/выбору билета или задерживает действия.
- Не писать фиктивные отзывы, актёрский состав, награды, расписание или адреса; контент берётся из утверждённых источников театра.

## 8. Тесты, CI и готовность задачи

Задача не считается завершённой, пока:
- код типизирован и форматирован;
- добавлены/обновлены unit tests для бизнес-правил;
- добавлены integration tests для DB-транзакций и идемпотентности, если меняется транзакционный код;
- для UI затронутого ключевого потока есть проверка поведения/адаптивности;
- `lint`, `typecheck`, tests и production build проходят;
- документация и `tasks.md` обновлены;
- не добавлены лишние зависимости и не утекли секреты.

Обязательные платёжные сценарии в тестах: duplicate webhook, неверная сумма, неверная валюта, платёж отменён, webhook задержан/повторён, timeout создания платежа, expiry hold, оплата после expiry, повторный возврат, email API unavailable, отсутствие доступного остатка при конкурентной покупке.

## 9. Поведение coding agent

- Перед изменением объяви задачу и краткий план в своём ответе/PR.
- Сначала изучи текущий код и связанные тесты; не предполагай, что файлы соответствуют документам.
- Не удаляй существующую функциональность ради прохождения нового теста без явного решения.
- Не подавляй ошибки TypeScript через `any`, `@ts-ignore` или отключение lint без документированного основания.
- Не оставляй фиктивные кнопки, заглушки, `TODO` в критичных потоках или тесты, которые только проверяют `true`.
- Если ответ банка/правовая трактовка/текст документа не подтверждены, пометь задачу `BLOCKED` и реализуй безопасный абстрактный слой вместо выдуманного значения.
- Не переключай домен, не отключай Ticketscloud, не запускай реальные платежи/возвраты и не меняй продуктивные секреты в рамках автоматической задачи без явного чек-листа и разрешения владельца.
- В финальном отчёте перечисляй изменённые файлы, проверки и оставшиеся риски. Не заявляй, что тесты прошли, если они не запускались.
